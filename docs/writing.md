# 中文写作规范细则

本文补充 AGENTS.md 的 Writing 一节。适用范围、总体原则和核心规则写在 AGENTS.md 里，这里收录其余规则、核心规则的示例，以及修改已有文字时的要求。

## 核心规则示例

- 只写有依据的内容：
  - 改前：GPU 模拟让单位上限提高了 100 倍。
  - 改后：GPU 模拟能承载多少单位，尚未实测。
- 不用“不是 X，而是 Y”制造对比：
  - 改前：这不仅仅是一个 CPU 版的模拟，更是 GPU 版的正确性基线。
  - 改后：CPU 版的模拟也是 GPU 版的正确性基线。
- 不要拔高：
  - 改前：完整实现了泰伯利亚矿的调色板动画，彰显了对原版细节的极致追求。
  - 改后：实现了泰伯利亚矿的调色板动画。
- 文档只写改完以后的状态：
  - 改前：流场寻路会改变模拟的整体结构，已经放进里程碑 2。
  - 改后：删掉这句。流场寻路只写在里程碑 2 的内容里。

## 句子

- 列举时有几项就写几项，不要为了凑满三项硬加一项，也不要为此把不同的东西并成一项。
- 不要用一连串短句或单独成段的短句制造戏剧效果，同一个意思合成一句。连续几句都用同一个主语开头、读着拖沓时，也可以合并。
- 按大家平时的说法写。不要拆开固定搭配，不要自己生造搭配或标签，也不要为了效果故意重复或回环。
- “的”字叠得太多、定语太长时，把句子拆开。
  - 改前：这是一个基于 compute shader 的支持上万个单位的流场寻路方案。
  - 改后：寻路用流场实现，流场由 compute shader 计算，要能支持上万个单位。
- “进行＋动词”一般换成直接的动词，比如“对单位缓冲区进行重构”写成“重构单位缓冲区”。
- 该用“是”“有”的地方直接用，不要绕成“作为……”“设有……”。
- 不要堆砌四字词。“稳定可靠、高效便捷”这类没有具体内容的组合，要么换成实际的特性，要么删掉。
- 执行者明确时用主动句，并写清楚是哪个部件在执行、等待或做决定，比如 CPU、GPU 还是某个 compute pass。代词可能指代多个对象时，直接写部件名。不知道执行者时可以用被动句，不要硬补一个“系统”之类的主语。
- 同一层不确定性只说一次，不要把“也许”“可能”“大概”叠在一起。
- 破折号可以用来插入说明，但不要拿它制造悬念，或者代替“因为”“但是”。

## 内容和篇幅

- 按顺序讲，不要先罗列几项，再用冒号引出一句总结。
- 连贯的说明写成段落。不要为了显得清楚，把一段论述拆成要点列表。
- 写出具体关系，不要用“密切相关”“紧密结合”一笔带过。比如“寻路与地形密切相关”应该写成“地形改变以后，经过这块地形的流场要重新计算”。
- 不要反驳没人提出的意见，比如“这并不是说 CPU 版没有用处”。真实存在的限制和反对意见要保留。
- 不要用格言或比喻代替具体的判断。
- 不写客服腔，比如“好问题”“希望对你有帮助”。
- 架构、UI 这类设计文档只写宏观设计、模块边界和不写就容易出错的约束，不写实现过程和细节。参数、数据格式和调用顺序留在代码和注释里，文档写明在哪个文件就够了。
- 设计文档和操作指南不收录测试结果、性能测量或构建通过记录。测量数据留在报告中，任务完成情况写在 `docs/plans/`。

## 格式

- 粗体只用于读者跳读时需要抓住的重点和警告，不要拿来装饰。
- 标题和正文里不加表情符号、箭头或分隔线作装饰。

## 修改已有文字时

- 用户只要求审阅时，给出修改建议，不要直接改文件。
- 润色只改表达。没有要求时，不要顺带扩写、缩写、补论据或改观点。
- 只改确实有问题的地方，读着顺、意思清楚的段落保持原样。保留作者原来的语气、用词习惯和文体；原文没写细节的地方，改完也可以保持概括。
- 发现疑似事实错误时，单独向用户指出，不要直接换成自己猜的答案。
- 改完的文档不能留下指向旧版本的话，比如某项“已经放进里程碑 2”“移到了 2-3”“原计划是……”。读者没有看过旧版本，这种话只会让人去猜改了什么。内容移走以后，原处直接删掉；读者确实需要知道去哪里找时，才写“见里程碑 2”这样的引用。
- 改完后对照原文，检查有没有新增、遗漏或加强的说法，以及条件、范围、否定和时间是否和原文一致。
- 代码块、行内代码、命令、路径、链接和标题都不要改动，以免破坏引用和锚点。表格数据和列表项的顺序也保持不变。
