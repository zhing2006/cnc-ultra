# 测试宪法

版本 0.1.0，批准于 2026-10-24。

## 第一条 测试只为拦住功能缺陷

每一个测试都要能拦住真实的功能缺陷：代码出错时它会失败，代码正确时它会通过。写测试之前，先想清楚它要拦的是哪一种错误。如果说不出来，这个测试就不写。

## 第二条 不写防御性测试

不为程序里不会出现的输入和走不到的分支写测试，也不为了提高覆盖率去测常量、简单的取值函数或者框架本身的行为。只检查“没有抛异常”“返回值不是空”的测试也不写，因为结果算错了它照样会通过。

## 第三条 不为删掉的功能写反向测试

功能删掉以后，它的测试也一起删掉。不要再写测试去证明这个功能已经不存在了，比如断言某个按钮不再显示，或者某个函数不再导出。

## 第四条 判断依据来自原版

测试判断对错的依据来自原版，不来自当前的实现。文件格式对照原版源码和 OpenRA 的解析代码，游戏规则对照原版源码，画面对照原版游戏的截图，或者对照另一个独立解码器的输出。本项目自己的输出不能录下来当作基准，因为那样只能说明代码没有变化，说明不了它是对的。

## 第五条 确定性要有测试

模拟必须是确定的（见技术宪法第六条），所以要有测试去检查这一点：同样的初始状态加上同样的命令序列运行两遍，两次的模拟状态要逐位相同。并行写入冲突、读回时机这类问题，只有这种测试才拦得住。

## 第六条 修缺陷先写复现测试

发现功能缺陷以后，先写一个能复现它的测试，确认这个测试失败，再去修代码。修好以后，这个测试留下来，防止同一个缺陷再出现。

## 第七条 测试在哪里运行

不需要 GPU 的逻辑，比如文件格式解析、定点数运算和游戏规则，用 Vitest 在 Node 里测试。需要 GPU 的部分，比如渲染和 compute shader，用 Playwright 在支持 WebGPU 的 Chromium 里测试。

## 第八条 并行运行，复用状态

测试套件要尽可能并行运行，互不依赖的检查同时进行。开发服务器、浏览器和已经打开的页面这类状态只准备一次，由多个检查共用。不要在每个用例之前把状态还原一遍：如果前一个检查留下的状态正好是后一个检查的起点，后一个检查就接着往下做。只有前提条件互相冲突时，才分别准备状态，比如一个检查要求 GPU 设备创建失败，另一个要求设备正常。
