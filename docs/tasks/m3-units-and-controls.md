# 里程碑 3：单位和操作

## 目标

车辆和步兵按原版的类型数据移动，玩家可以像在原版里一样选择单位、下达移动命令。视野和迷雾在这一步做，单位被选中和接到命令时也会回话。

## 原因

从这一步开始，游戏第一次能上手操作了。原版玩家最先感觉到的，就是选择、下命令和单位移动的手感，这些都要照原版来做（设计宪法第三条）。

里程碑 2 的流场全图只有一个目标，换目标就从头算。距离场每个逻辑帧只松弛固定的次数，收敛以前单位不出发，在 scg08eb 上抽样测过，最多要等 3 个逻辑帧。到了这一步，玩家会给不同的单位下不同的命令，下令以后单位反应得快不快，也是玩家最先感觉到的手感之一，所以流场要按目标分开，反应的时机也要和原版一样。

## 范围

要做：

- 从原版移植车辆和步兵的类型数据，包括速度、转向速度、视野和造价。
- 车辆的朝向、转向和移动，步兵走路的动画。
- 单位被友军挡住时，按原版的规则等待或者绕开。
- 流场按目标分开。同一个目标的单位共用一个距离场，同一时间对同一个目标只算一次（技术宪法第五条）。给一部分单位下新命令时，别的单位正在用的距离场不受影响。没有单位再用的距离场要回收，显存不能随下令的次数一直增长。
- 下令以后，单位从哪个逻辑帧开始转向或出发，和原版一样。原版在命令执行后的下一个逻辑帧里当场算出路径，所以在原版尺寸的地图上，算距离场不能让单位比原版晚出发。地图变大以后，算距离场的时间会随路径变长而增加。在一张 256×256 格、需要绕远路的测试网格上实测这段延迟，写进本文件（技术宪法第十三条）。
- 点选、框选、移动命令和光标的形状（设计宪法第三条）。
- 原版快捷键里和选择、移动有关的部分。
- 视野和迷雾在 GPU 上计算。原版的迷雾揭开以后就不会再盖上。
- 视野的透视层。
- 解析和播放 AUD 音频，单位被选中和接到命令时的语音。

不做：

- 攻击和其他战斗，放在里程碑 4。
- 侧边栏、雷达和建造，放在里程碑 5。
- 飞机，放在里程碑 6。
- 适合几千个单位的选择方式，放在里程碑 8。

## 验收标准

- 同一辆车在空地上走同一段直路，用的逻辑帧数和按原版数值算出来的一样。（自动测试）
- 一辆车原地转一整圈，用的逻辑帧数和按原版的转向速度算出来的一样。（自动测试）
- 在 scg08eb 上向远近不同的几个目标下令，单位开始转向或出发的逻辑帧和按原版规则算出来的相同。（自动测试）
- 两组单位分别走向两个目标，其中一组换目标时，另一组的距离场和行走不受影响，GPU 版和 CPU 版的校验和相同。（自动测试）
- 一个单位揭开的格子，和按 `MapClass::Sight_From` 的规则算出来的相同。（自动测试）
- AUD 的解码结果和 OpenRA 解出来的采样相同。（自动测试）
- 点选、框选、下命令的方式和光标的变化都和原版一致，单位接到命令会回话。（试玩检查）

## 开发约定

- 试玩使用 scg08eb 的地形，专门放置多种车辆和步兵，保留单独入口，方便检查速度、转向、动画和分组命令。
- `Alt+Enter` 切换由页面发起的全屏，并在全屏时启用 Keyboard Lock，以接收原版编队快捷键。原版 `CONQUER.CPP` 的 `Keyboard_Process` 没有占用这个组合。全屏入口不增加面板或按钮，操作说明同步写入中英文 README。
- 保留后台暂停和手动暂停。功能和测试全部写完后统一跑检查，调试具体问题时可以运行相关检查。
- 整组移动保留各类型的原版速度，修复循环互等和因临时拥堵而在远处放弃命令的问题。
- 流场池按内存预算设置容量。如果同时使用的不同目标超出容量，允许在池满时轮换计算，让部分目标暂时等待；这是原版地图下令后不额外等待的唯一容量例外。没有池满时，新命令不打断其他单位正在使用的距离场。

## 开发记录

- 试玩入口是 `?demo=units`，放置 28 辆车和 35 名步兵。默认地图和 M2 的 `?demo=simulation` 保留原来的用途。中英文 README 列出了入口、选择和编队快捷键，以及 `Alt+Enter` 的全屏操作。
- `src/game/data/movement.ts` 保存了 42 种车辆、步兵的速度、转向速度、视野、造价、生命值和走路动画数据。`tracks.ts` 保存车辆的 13 组移动轨迹及 67 项转向配置。两部分数据都与 Nyerguds 版本逐项核对过。
- `src/game/simulation/units-cpu.ts` 和 `units-gpu.ts` 处理移动、转向、占位、等待和散开。命令按照 `CONQUER.CPP` 的 `Main_Loop` 和 `QUEUE.CPP` 的 `Queue_AI_Normal`，在当前逻辑帧的单位更新之后执行。车辆使用 `DRIVE.CPP` 的轨迹坐标，连续转弯时按 `While_Moving` 的 Jump、Entry 和 Cell 处理轨迹衔接。迎面车辆按 `UnitClass::Can_Enter_Cell` 绕开；不可达目标在重试结束后清除。步兵按 `InfantryClass::Start_Driver` 保留起点的子格坐标，倒退目标点后调用 `CellClass::Closest_Free_Spot` 的选位规则。格子内按单位编号依次预留空位，五名步兵可以在同一个逻辑帧起步。
- `navigation.ts` 按 `FootClass::Basic_Path` 的顺序查找山崖目标周围的合法格子。玩家点击的格子保留在命令里，流场使用单独的实际寻路目标。同一组单位可以从各自所在的一侧靠近山崖。没有合适邻格时，沿目标方向查找可通行路段，并继续检查途中障碍的后方，把绕开障碍的路线交给流场计算。因此，朝湖中间下令时，沿途的一棵树不会让单位提前停下。这个处理依据 `Find_Path` 穿过障碍寻找下一段通路的规则，没有移植原版的 `Follow_Edge` 路线算法。
- 流场路线遇到持续等待的友军时，在一个 `PATH_DELAY` 间隔后重新尝试绕行。相邻的绕行格必须缩短流场距离，不能把退回原地当成寻路成功。静止友军按 `DriveClass::Start_Of_Move` 的 `MOVE_TEMP` 处理收到让路请求；无法绕开的迎面车辆消耗寻路重试次数，最终结束命令。暂时被移动中的友军堵住时继续等待。终点附近仍使用原版的停车距离和格子占位规则。
- 步兵的落脚坐标使用 `Closest_Free_Spot` 收到的倒退坐标所在格，可能先在当前格内挪一步，再进入下一格。占位先处理离开格子的步兵，再给短距离移动预留空位，两部分在同一个逻辑帧内完成。到达中间落脚点后继续走向先前选定的邻格，不把原地踏步当成一次成功的移动。
- `src/engine/simulation/flow.ts` 按目标复用距离场，池容量最多 64 个槽位，并受单块距离缓冲区 16 MiB 的预算限制。单位并行登记目标，相邻的重复目标只登记一次，调度只遍历目标位图和槽位。池满时按目标轮换，尚未收敛的场会继续计算到收敛。原版尺寸的网格仍由一个 workgroup 在一次逻辑更新里完成一个目标的求解，只扩展上一轮改变的格子，用 workgroup 原子标志判断收敛。
- 大于 4096 格的网格使用 `flow-tiles.ts`，每个 16×16 区域交给一个 workgroup。每次逻辑更新交换 8 次区域边界，每次在固定边界内最多松弛 16 轮。区域之间读写分开的距离缓冲区，dispatch 边界保证同步，CPU 版使用相同的更新顺序。256×256 网格的一个活动目标会派发 256 个 workgroup；间接派发列表只包含未完成的目标。两种求解方式都只在收敛时生成方向，distance、scratch 和 next 的内存预算相同。
- GPU 回归把 17 个场景放在两张 64×64 测试地图的隔离区域里，共用模拟实例。独立的 CPU 复现用例保留原来的地图和种子，GPU 场景使用合并地图的单位编号和固定种子。每个场景原有的检查帧、结束时间和停止验证都保留。没有新命令的一段逻辑帧可以批量提交，模拟仍逐帧执行。循环变量和 storage buffer 使用稳定的 shader 名称，便于相同程序复用编译缓存。
- 点选、框选和编队在 GPU 上处理，选择与编队使用独立的本地界面缓冲区，不参与模拟校验和。移动命令在点击时记录所选单位，后续改变选择不会改变已经下达的命令。CPU 只异步读取少量结果，用于语音和镜头定位，不读取整份单位状态来更新画面。普通点击组内已选单位保持整组选择，也不重复播放语音。
- `sight.ts` 按 `MAP.CPP` 的 `Sight_From` 揭开地图，并保留 `DISPLAY.CPP` 的 `Map_Cell` 递归顺序和 `Cell_Shadow` 边缘判断。当前视野按单位并行写入。只有进入新格子、且视野内仍有未揭开格子的单位才进入顺序揭图阶段。已经揭开的格子不会重新盖上。画面使用原版 `SHADOW.SHP` 和阴影映射表。
- 可见但不能进入的格子显示禁止移动光标，迷雾里仍显示可移动光标。两种情况都会下达移动命令并回话，依据 `TechnoClass::What_Action`、`DisplayClass::Mouse_Left_Up` 和 `FootClass::Active_Click_With`。允许移动时播放原版 `MOVEFLSH.SHP`，使用 `TWHITE.MRF` 的白色半透明映射，并按 `AnimClass::Sort_Y` 加入地面绘制顺序。
- 加入了 `assets/dev/sounds.mix`。AUD 解码支持原版数据里的 Westwood 压缩和 IMA ADPCM；语音选择及单位声音变体依据 `UNIT.CPP`、`INFANTRY.CPP` 和 `AUDIO.CPP`。`tests/reference/export-aud.ts` 调用固定版本的 OpenRA 解码器生成 PCM 摘要，仓库不保存解码后的音频。

## 验证记录

2026-10-24，Windows，NVIDIA GeForce RTX 5090 D，驱动 32.0.16.1664，Chromium 156.0.8078.4。

- `pnpm check`：`svelte-check found 0 errors and 0 warnings`。
- `pnpm test`：9 个测试文件通过，521 项测试通过。其中 120 项逐一比较原版音频与 OpenRA 解码结果的 PCM 摘要。
- `pnpm test:e2e`：6 项检查通过，输出 `browser checks passed (36.8s total)`。M2 的检查同时通过。
- 坦克、步兵和混合场景各运行 100 个逻辑帧，抽样比较完整 CPU/GPU 状态、校验和、重复执行结果、当前视野、已经揭开的地图和迷雾边缘。scg08eb 的混合部队另外运行 90 帧，对照地面图层顺序和动画像素。
- scg08eb 上的近、远目标检查了命令执行后的下一个逻辑帧：单位已经开始进入移动轨迹，或者已经设定转向目标，不再因为等待距离场而延迟。原地转过四个直角时，中型坦克按照转向速度 5 使用 52 次转向更新。
- 移动帧数的复核覆盖了 `COORDA.ASM` 的四舍五入，以及 `DISPLAY.H` 中 `256 / 24` 的整数除法。回归检查先复现了取整方式错误造成的移动变慢，再验证修复。测试在第 1 帧执行移动命令，中型坦克沿空地直行一格在第 32 帧到达，道路上在第 23 帧到达，受损后的空地移动在第 42 帧到达。
- 256×256 网格中，在第 128 列放置从第 0 行延伸到第 253 行的障碍，目标在障碍另一侧。距离场经过 4 次逻辑更新收敛；按 15 Hz 推进时相当于约 0.27 秒的求解等待。预先创建 shader 后，从下达新目标到观察到收敛，最终完整检查记录为 101.97 ms，包含每次观察状态的异步读回。这是测试循环的耗时，不是按真实 15 Hz 等待的墙钟时间。
- 浏览器检查覆盖点选、原版编队快捷键、`Alt+Enter` 进入和退出全屏、移动、语音调用、透视层开关及暂停。已经查看试玩截图。原版手感和声音仍需项目负责人试玩验收。

- 新增回归检查先复现了不可达目标不退出、迎面车辆互等、步兵选位错误和缺失轨迹跳转，再验证修复。浏览器检查比较了这四类场景的 CPU/GPU 状态，还检查组内点选、选择与编队不改变校验和、禁止移动命令、迷雾光标、移动闪标的起始帧和消失时机。白色半透明效果与按原版映射表顺序绘制的参考结果逐像素比较。
- 山崖和整组移动补充了 6 项单元测试，覆盖从两侧靠近山崖、相邻山崖停车、邻格被占时的选择顺序、保留可通行路段、四辆车循环互等，以及 4 辆车和 10 名步兵通过单格路口。浏览器检查比较对应场景的 CPU/GPU 状态，混合部队场景运行 2200 个逻辑帧，所有单位均到达目标附近。修复前的定向检查复现了山崖目标无法起步、近处目标不清除和循环互等；补充检查也复现了可通行路段没有保留的问题。
- 目标池检查使用两万条目标记录和 100 个不同目标，验证池满后的轮换以及 CPU/GPU 状态一致。256×256 网格使用两万条相同目标记录时，池容量为 64；distance、scratch 和 next 申请的缓冲区各为 16 MiB，共 48 MiB，仍在默认设备绑定上限内。
- 使用 GPU timestamp query 单独测量 compute pass，排除 shader 编译、CPU 提交和状态读回。在上述 256×256 绕路网格上，4 次逻辑更新各约 0.59 ms；收敛后的下一次更新为 0.52 ms。优化前同机记录为 8 次更新、每次 4.26～6.62 ms，收敛后为 0.33 ms。分块计算缩短了求解时间，但缓存命中时增加了约 0.19 ms 的派发开销。该测量使用两万条目标记录，不代表两万单位的完整模拟。硬件的 SM occupancy 百分比未实测。
- 视野测量使用 256×256 网格上的一万辆中型坦克。首次揭图后，静止时一次视野更新为 0.07 ms；将所有单位向东移动一格后，一次更新为 0.92 ms。这些数值只表示视野模块的 GPU 耗时。
- 首轮完整检查发现 20 个类型错误，修复后 `pnpm check` 输出 0 错误、0 警告。同一轮的 M2 点击检查发生一次“No move command received”超时，单独排查和整套复跑均通过。移动闪标起始帧的补充修复之后，类型检查和 M3 定向浏览器检查也通过。
- 山崖处理的完整检查曾发现 CPU/GPU 状态不一致。定位到生成的 shader 在另一条分支中读取了未赋值的目标坐标后，改为在分支前显式保存坐标中间值。定向检查和最终完整检查均通过。
- 后续审阅指出，整组移动测试只检查到达附近，没有检查单位是否停下。补充的回归检查先复现了 9、12、16 辆中型坦克、12 辆吉普、30 名步兵聚集后仍握着命令，单格通道内两车反复退让，朝水面下令时被沿途树木截停，以及步兵落脚格错误。原有混合部队测试加上命令结束断言后也失败了。修复后的定向检查通过：聚集场景运行 3000 帧，再检查 600 帧内保持停止；混合部队既要全部靠近目标，也要结束命令并停止移动。
- 移动问题修复前的定向检查为 9 项失败、16 项通过；修复后的 25 项全部通过。浏览器增加了水面前有树、单格通道迎面车辆、步兵先在当前格内落脚，以及 16 辆中型坦克、12 辆吉普、30 名步兵分别聚集的场景。CPU/GPU 状态一致，聚集、通道和混合部队场景在命令结束后的 600 帧里保持停止。
- 测试优化前，浏览器检查耗时 91.0 秒，优化后为 36.8 秒。合并后的 GPU 移动回归执行 7200 个世界逻辑帧，构建模拟实例用时 4.83 秒，CPU 推进、断言和 GPU 提交合计 0.37 秒，读回及等待 GPU 合计 1.29 秒。这些是浏览器侧的墙钟计时，不是单项 GPU 耗时。
