# 里程碑 4：战斗

## 目标

地面单位之间按原版的规则交战，包括攻击命令、自动选择目标和还击、炮塔转向、子弹、爆炸和伤害，以及武器和爆炸的音效。

## 原因

一局对战要靠战斗分出胜负，规则和数值都要和原版一致，原版玩家才认得出来。子弹和伤害都在 GPU 上结算（技术宪法第五条）。很多颗子弹同时打中同一个单位，是并行写入冲突最集中的地方，结果必须是确定的（技术宪法第六条），所以这一步要特别检查确定性。

## 范围

要做：

- 从原版移植武器和弹头的数据。伤害按原版的公式计算，包括弹头对不同护甲的修正和爆炸的范围伤害。
- 攻击命令、自动选择目标、受到攻击时还击、射程、射速和炮塔的转向。
- 子弹的飞行、爆炸动画，以及地上留下的弹坑和焦痕。
- 单位被摧毁时的爆炸，步兵的死亡动画。
- 武器和爆炸的音效。

不做：

- 建筑和防御建筑，放在里程碑 5。
- 飞机和防空，放在里程碑 6。
- 工程师、突击队这类单位的特殊能力，放在里程碑 6。

## 参考

原版源码在 `refs/source/cnc-tiberian-dawn/`：

- `CONST.CPP` 的 `Weapons` 和 `Warheads`：武器和弹头的数据。
- `COMBAT.CPP` 的 `Modify_Damage` 和 `Explosion_Damage`：伤害的修正和范围伤害。
- `TECHNO.CPP` 的 `TechnoClass::Greatest_Threat`、`TechnoClass::Can_Fire` 和 `TechnoClass::Fire_At`：选择目标和开火。
- `TURRET.CPP`：炮塔。
- `BULLET.CPP` 和 `BBDATA.CPP`：子弹。

## 验收标准

- 每一种武器打每一种护甲，一发造成的伤害都和原版公式算出来的一样。（自动测试）
- 两辆车对射，摧毁对方用的逻辑帧数，和按原版的射速、伤害算出来的一样。（自动测试）
- 很多颗子弹同时打中同一个单位时，GPU 版和 CPU 版的结果逐位相同。（自动测试）
- 两队单位交战时，自动选择目标、还击和炮塔转向的表现和原版一致，音效对得上。（试玩检查）

## 讨论结果

- 使用单独的战斗试玩入口。玩家指挥 GDI，敌军留在阵地警戒，发现目标后按原版规则交战。
- 车辆被毁后的幸存乘员也在本次范围内，按 `UNIT.CPP` 的 `UnitClass::Take_Damage` 处理生成条件、兵种和生命值。
- 实现和测试代码完成以后统一跑检查；定位具体问题时可以运行相关检查。

## 开发记录

- 增加 `?demo=combat`，在 scg08eb 上布置 GDI 和 Nod 地面部队。Nod 在东侧警戒，玩家可以移动、攻击单位或用 Ctrl 加左键攻击地面。操作说明已经写入中英文 README。
- 从 `CONST.CPP`、`BBDATA.CPP`、`UDATA.CPP`、`IDATA.CPP` 和 `ADATA.CPP` 整理武器、弹头、弹丸、单位战斗属性和动画数据。用 Nyerguds 的对应表格交叉核对，采用 EA 原版数据。
- CPU 和 GPU 共用整数数据表，分别实现战斗更新。弹丸按单位预留 8 个槽位；寻敌使用格子索引，命中按弹丸并行计算。一次爆炸按照中心格及八个方向收集最多 32 个对象，不包含开火者。多个弹丸同时命中时累加整数伤害，由编号最小的命中弹丸提供本轮伤害归属。
- 死亡引发的连锁爆炸在同一逻辑帧里处理完。队列的初始顺序来自单位编号；后续死亡按爆炸收集顺序进入队列。幸存乘员使用预留的步兵位置，按原版的概率、兵种和生命值范围生成，并尝试散开。
- 炮塔独立于车身转动。步兵有开火、卧倒、起身和死亡动画，卧倒会影响伤害与移动速度。爆炸和烟雾读取 `TTRANS.MRF`，按照源像素选择映射表，再转换下面的像素。弹坑按落点选择形状，重复命中会加深。
- 声音通过有数量上限的异步事件读回播放，同类音效限制重叠。弹丸和单位状态留在 GPU 上。

## 验证记录

开发机使用 NVIDIA GeForce RTX 5090 D，驱动 32.0.16.1664，Chromium 156.0.8078.4。

- 单元测试覆盖 25 种武器与 5 种护甲的伤害取整、爆炸衰减、炮口坐标、射速、对射死亡帧、32 个对象上限和幸存乘员。中型坦克对射用例中，第一发在第 2 帧射出，第 11 帧命中，此后间隔 53 帧；400 点生命值的目标在第 700 帧被摧毁。
- 浏览器检查比较了混合武器场景的 780 个逻辑帧、整队从起点进攻阵地的 450 帧，以及 256 发炮弹同时命中。检查还逐像素比较了爆炸、烟雾、车辆和地面叠加时的索引值。
- 性能场景在 256×256 格的空地上放置两万个单位，交错排列双方的中型坦克和步兵。初始化后第 3 至第 5 个逻辑帧的移动与战斗 compute 合计约 0.66～0.79 ms，来自 GPU timestamp query，不包含视野、渲染和音频读回。持续混战、大量同时死亡时的耗时、整场渲染帧率和其他显卡的结果未实测。
- 首轮类型检查发现 14 处错误，涉及 TSL 指针参数、推断过窄的类型以及数据表中的常量表达式；修复后通过。后续缩减试玩素材集合时又发现 3 处集合类型错误，已经修复。
- 首轮浏览器检查发现测试模块路径错误，并出现一次 M2 点击超时。路径已经修正；共享浏览器的鼠标锁定与全屏操作改成轮流执行，模拟检查仍然并行。后续整套浏览器检查通过。
- CPU/GPU 对照发现负方向位移的取整顺序差了 1 个 lepton，已经修复。对射死亡帧断言随后发现炮塔多等待一帧，改为使用本帧旋转更新后记录的状态，保留原有期望值后通过。

最终 `pnpm check` 输出 0 错误、0 警告；`pnpm test` 输出 10 个测试文件、552 项测试通过；`pnpm test:e2e` 的 7 项检查全部通过，总耗时 39.9 秒。最终性能样本为 0.66、0.79、0.72 ms。已经查看交战场景截图。

原版操作手感、战斗表现和声音仍需试玩验收。

## 试玩问题修复

自动检查通过不代表全部单位行为已经与原版一致。

首次框选会触发选择 compute pipeline 的编译。选择和周期性校验和的 pipeline 现在都在载入时准备，第一帧提交并完成以后才开放操作。页面从 HTML 启动阶段就显示载入提示，随后显示读取文件、准备战场和画面等实际阶段。素材预览页也有提示。README 保留产品说明、体验入口和基本操作，详细开发记录留在任务单中。

整队攻击时，后排可能在前排占住接近路线以后反复使用同一个走不通的目标。原版 `FOOT.CPP` 的 `FootClass::Approach_Target` 会寻找射程内的位置，`FINDPATH.CPP` 的 `Find_Path` 能把动态障碍算进路线。这里保留原版的射程和移动速度，在接近射程且路线受阻时，增加单位周围 17×17 格的搜索。搜索会避开占用格，记录要去的位置，再逐格接近；途中不改变整队速度。远处的移动仍然使用流场。

回归场景让 40 辆中型坦克攻击一个高生命值目标。修复前，第 2000 帧仍有一辆满血坦克从未开火；修复后所有存活坦克都开过火，CPU/GPU 状态对照覆盖完整的 2000 帧。测试没有放宽帧数限制，也没有只检查“已经靠近”。大规模拥堵时同时触发局部搜索的耗时未实测。

首次框选在上述 RTX 5090 D、Chromium 156.0.8078.4 环境中复测。修复前，选择命令的 CPU 提交约 9.22 ms，异步结果等待约 41.51 ms；修复后对应样本为 0.11 ms 和 2.71 ms。连续三次框选都没有新建 compute pipeline，三个采样窗口中的最大渲染帧间隔分别为 6.01、5.98、6.17 ms。这些是本机样本，其他设备未实测。

本次首轮检查发现 11 处 TSL 数组索引类型错误，重启检查也在等待首帧时超过了原有的 5 秒时限。修正类型声明，并将重启等待时限调整为 30 秒后，`pnpm check` 输出 0 错误、0 警告；`pnpm test` 的 10 个文件、553 项测试通过；`pnpm test:e2e` 的 8 项检查通过，总耗时 44.9 秒。载入检查会暂缓文件响应，验证提示保持可见，再检查首次框选没有新建 pipeline。两万个单位的原有性能场景测得 0.85、0.85、0.66 ms，测量范围和前面的性能记录相同。

后续试玩发现敌方步兵卧倒时变黄，以及敌方坦克的炮塔朝向没有正确显示。步兵问题来自绘制槽：车辆的炮塔需要第二个槽，步兵的第二个槽原本为空，但战斗动画也在里面画了一个使用默认黄色的步兵。按照 `INFANTRY.CPP` 的 `InfantryClass::Draw_It`，步兵动作现在只替换主体，保留其阵营配色。

炮塔问题来自生成的 shader：TSL 将战斗状态索引缓存到步兵分支，车辆分支读取时没有初始化，因而误用了 0 号单位的炮塔朝向。共享索引现在在进入分支前显式初始化。回归检查让双方炮塔指向不同方向，按 `UNIT.CPP` 的 `UnitClass::Draw_It` 检查各自的精灵帧；同时检查步兵卧倒、开火和死亡时只绘制一个主体，并保留原有配色。两个问题都先在修复前复现，修复后专项检查通过。

这两处修复完成后，`pnpm check` 输出 0 错误、0 警告，`pnpm test` 的 10 个文件、553 项测试通过，`pnpm test:e2e` 的 8 项检查通过，总耗时 45.2 秒。

随后修正了喷火方向与动画索引，补上敌方步兵碾压，并按原版继续核对开火和移动的衔接。新增检查覆盖副武器尝试、炮口整数偏移、移动时的卧倒条件、锁定炮塔和停下后的部署等待。修正与尚未覆盖的行为见下文“单位行为核对”。本轮最终类型检查通过，559 项单元测试和 8 项浏览器检查通过；浏览器检查耗时 66.3 秒。

## 单位行为核对

核对日期：2026-10-24。参考 EA 原版源码，以及 Nyerguds 的 `CODE/`。这里记录代码核对和测试覆盖，不代表已经用原版游戏逐帧验收全部单位。

### 数据

重新检查了 42 种地面单位的战斗数据、25 种武器、12 种弹头、19 种弹丸和 78 种动画。动画必须按 `ADATA.CPP` 的 `AnimTypeClass::Pointers` 排列，不能按构造对象的声明顺序排列。此前火焰方向因此左右颠倒，已经修正，相关动画引用也一起按原版枚举重排。

Nyerguds 的单位数据有两处需要区别：`UnitMLRS` 的体型标志不同；`E5` 的胆怯标志和出现关卡不同。这里采用 EA 原版数据。弹丸和动画构造数据没有发现差异。数据检查不能替代下面的行为检查。

### 本轮修正

- `TECHNO.CPP` 的 `Fire_At`：火焰和机枪方向动画使用开火朝向。弹丸从偏移炮口瞄准目标时，方向可能与车身不同，不能拿弹丸方向决定火焰素材。
- `TURRET.CPP` 的 `Fire_Coord`：炮口向北偏移也经过 `Coord_Move`。原来的直接减法绕过了整数三角表，部分炮口差了 1 个 lepton。
- `TARCOM.CPP` 的 `AI`：主武器不能开火时继续检查副武器，包括炮塔还在转动的情况。猛犸坦克因此可以先发射满足条件的导弹。
- `TARCOM.CPP` 的 `FIRE_FACING`、`TURRET.CPP` 的 `Ok_To_Move`：锁定炮塔的火箭车需要转动车身，起步也要等待炮塔对齐。
- `UNIT.CPP` 的 `Per_Cell_Process`：火炮和火箭车完成移动后，有 18 个逻辑帧的部署等待。
- `INFANTRY.CPP` 的 `AI`：按 `SPECIAL.H` 默认的 `IsDefenderAdvantage`，步兵执行移动命令时不会直接卧倒。
- `UNIT.CPP` 的 `Can_Enter_Cell`、`DRIVE.CPP` 的 `Overrun_Square`：有碾压能力的车辆可以进入敌方步兵的格子，在原版的进格检查点按距离判定碾压。友军不会被压死，吉普等没有碾压能力的车辆也不能这样通行。被压死的步兵直接移除，留下 `SQUISH` 并播放 `SQUISH2`，不触发普通死亡的连锁爆炸。多个车辆申请同一格仍然需要争用预约。

### 验证范围

新用例先复现了碾压缺失、火焰方向错误、主副武器选择、炮口偏移、移动时卧倒、锁定炮塔的车身朝向和部署等待问题。浏览器检查还读取实际绘制记录，检查阵营配色、炮塔和火焰素材。

战斗场景通过真实的选择命令路径下达整队攻击，对照 CPU/GPU 状态并检查敌方车辆和步兵均能死亡。单独的 2000 帧排查也观察到了双方掉血和死亡，因此没有复现试玩反馈的“步兵和车辆都打不死”。这不能证明所有操作顺序都没有问题，仍需要结合具体场景继续定位。

碾压回归包含一格五名敌军、友军、没有碾压能力的吉普，以及两辆坦克同时申请一个目标格。GPU 只让到达进格检查点的车辆搜索对应格子，不让每个步兵每帧遍历附近所有车辆。

本轮检查结果：`pnpm check` 输出 0 错误、0 警告；`pnpm test` 的 10 个文件、559 项测试通过；`pnpm test:e2e` 的 8 项检查通过，总耗时 66.3 秒。首轮检查发现动画数据导出遗漏了 `18*7` 这类常量表达式的求值，已经修正。新增的 SAM 动画断言也曾错误地把素材帧序当作顺时针，重新对照 `ADATA.CPP` 后保留了原版的逆时针素材帧序。

在 NVIDIA GeForce RTX 5090 D、驱动 32.0.16.1664、Chromium 156.0.8078.4 上，原有两万单位场景的三个 GPU compute 样本为 0.79、0.79、0.85 ms。范围仍然是初始化后少量逻辑帧的移动与战斗，不包含渲染和视野，也不代表大规模实际碾压或持续混战的耗时。

完整单位行为仍未全部核对，M4 保持待验收。

## 测试耗时优化

2026-10-24，在 NVIDIA GeForce RTX 5090 D、驱动 32.0.16.1664、Chromium 156.0.8078.4 上，8 项浏览器检查从 66.3 秒降到 36.6 秒，缩短约 45%。这是本机两轮完整检查的墙钟时间，其他设备未实测。

耗时主要集中在重复构建移动与战斗的 shader。M4 的混合武器、同时命中、碾压和后排补位场景放在一张地图的四个独立区域中，共用一个 GPU 实例。区域之间保留不可通行地形和足够的距离，让初始警戒搜索互不影响。HUNT 使用全局搜索以后，后续单位可以发现其他区域中的敌人，CPU/GPU 对照仍然运行整个世界；独立规则用例另行判断寻敌是否正确。混合武器的 780 帧、碾压的 150 帧、后排补位的 2000 帧，以及 256 发炮弹同时命中的断言都保留。按原检查点的并集比较完整 CPU/GPU 状态。原版地图上的 1200 帧整队交战和两万单位性能场景继续分别运行。

M3 的三组基础移动、视野和回放检查也共用一张分区地图，GPU 实例从六个减少到两个。每个原检查帧仍比较完整状态、校验和与视野，三组选择和编队检查分别执行。独立 CPU 规则用例保留原来的坐标和种子；合并后的 GPU 场景使用所在世界的单位编号和固定种子。

没有新命令的连续战斗帧可以按批次提交，每帧仍执行完整的移动、战斗和占位更新。需要独立 compute pass 的间接派发路径继续逐帧提交。绘制记录检查与整队交战复用同一个初始 GPU 实例；前者改动的测试状态在后者开始前恢复。

离屏检查从空白测试页面启动，不再同时载入和绘制无关的游戏地图。实际界面检查仍然打开完整游戏页面。页面载入可以并行，只有需要鼠标和全屏焦点的操作轮流执行。M3 同一检查点只计算一次主实例的校验和，并行等待独立的读回结果。

最终 `pnpm check` 输出 0 错误、0 警告，`pnpm test` 的 10 个文件、559 项测试通过，`pnpm test:e2e` 的 8 项检查通过，输出 `browser checks passed (36.6s total)`。


## 战斗 review 修复

2026-10-24，根据目标、伤害、声音、特效与性能的 review 继续修正。下面记录本次修改，不代表范围之外的单位能力已经完成。

按 `FOOT.CPP` 的 `Mission_Guard`、`Mission_Attack`、`Mission_Hunt` 和 `Take_Damage`，警戒会定期放掉射程外的目标；指定攻击失效后退出攻击任务；HUNT 搜索整个战场，受到伤害时不随意换目标。全局搜索沿用 `TECHNO.CPP` 的非 `ADVANCED` 威胁评分，先按阵营归约候选和评分上界，再检查可能超过已有评分的附近格子。相同评分按单位编号裁决，不依赖线程顺序。原版地图与 Ultra 使用同一套逻辑。

发现敌军直接读取揭图系统。除了已经映射的格子，也处理原版 `DISPLAY.CPP` 的 `Map_Cell` 设置为 `IsVisible` 的部分迷雾边缘；发现状态会保留。没有目标的活动炮塔按 `TURRET.CPP` 的 `AI` 指向移动目的地。

按 `TECHNO.CPP` 的 `Fire_At` 和 `BULLET.CPP` 的 `Unlimbo`，移动开火也产生散布，散布落点按开火者的武器射程收回。步兵炮口按 `INFANTRY.CPP` 的 `Fire_Coord` 上移 5 像素，E4 例外。恐惧值按 `Take_Damage` 区分首次受击、半血、无攻击者和胆怯类型，保留 255 上限；E5 等胆怯步兵会在可中断动作时散开。

攻击和强制攻击使用各自的攻击应答表。步兵死亡按弹头和兵种选择惨叫，火焰、激光和粒子束使用 `YELL1`，突击队使用 `RAMYELL1`。原版 `DEFINES.H` 的 `SCREAM1` 至 `SCREAM5` 实际有四项，没有 `SCREAM2`，因此普通死亡保留四种声音。位置音效按 `AUDIO.CPP` 的 `Sound_Effect` 处理画面内外音量，归并同类事件时先保留画面内的声源，爆炸使用落点坐标。允许有上限的重叠播放，音频读回复用 `ReadbackBuffer`。

按 `UNIT.CPP`、`INFANTRY.CPP` 的 `Take_Damage` 和 `BULLET.CPP` 的 `AI`，补上受损车辆的附着烟雾、导弹隔帧留下的烟迹、E2/E4/E5 的死亡爆炸，以及载弹 SSM 的 `NAPALM3`。最大生命值超过 400 且带有爆炸的车辆被毁时产生震屏事件。震屏属于本地画面状态，不进入模拟校验和。

半透明合成同时支持位移和每像素只应用一次的白色映射。像素先沿位移追溯背景，再按绘制顺序应用映射。临时存储有固定上限，超过上限的重叠会分段追溯，保留全部贡献。测试包含位移、半透明和重叠白色映射，以及 40 层半透明。

普通伤害与死亡标记继续按单位并行，只有会引起连锁爆炸的死亡进入串行队列。没有连锁死亡时直接跳过队列构建。幸存乘员按格子并行分配，同一格内按父单位编号分配五个位置，随后统一处理散开。

后排补位使用每工作组 64 个线程的局部 BFS，按格子展开每一层，保存后续路线，并在终点被占或上一步没有到达时重新搜索。已规划好的相邻一步直接进入占位与移动流程，不再为它申请整张地图的流场。远距离移动仍使用流场。缓存、搜索结果与 CPU 参考实现保持相同的整数状态。

中英文 README 恢复了简短的静态部署说明，包括原版 MIX 文件、`data/` 目录和 COOP/COEP 响应头。

新增规则用例先复现了目标释放、攻击任务结束、HUNT、炮塔目的地方向、步兵炮口和恐惧值问题；语音用例也先复现了攻击命令误用移动应答。绘制检查先复现受损烟雾缺失，混合合成检查先复现位移与白色映射错误。首次集中检查发现两项单元用例失败和两项浏览器检查失败，涉及路线终点被占、旧对射用例没有隔离新的初始自动寻敌，以及 GPU kernel 超过默认八个 storage buffer 的绑定。后续调试还发现缓存可能跳过没有走到的上一格。上述问题均已修正。并行 BFS 调试中另外发现 TSL 没有保留条件表达式中的一次原子读取，显式保存读取结果后，逐帧 CPU/GPU 对照通过。


本轮最终验证：`pnpm check` 输出 0 错误、0 警告；`pnpm test` 的 11 个文件、569 项测试全部通过，耗时 922 ms；`pnpm test:e2e` 的 8 项检查全部通过，输出 `browser checks passed (47.5s total)`。浏览器检查新增了实际音频事件的声源优先级、重复播放、读回 buffer 复用和震屏事件，也检查了步兵死亡爆炸、导弹烟迹与载弹 SSM 的爆炸精灵。已经查看战斗截图。

性能环境为 NVIDIA GeForce RTX 5090 D，驱动 32.0.16.1664，Chromium 156.0.8078.4。以下为 GPU timestamp query 的本机样本，其他硬件未实测：

| 场景 | 准备阶段 | 移动 | 结算与视野 | 合计 |
|---|---:|---:|---:|---:|
| 两万个单位同帧死亡 | 0.13 ms | 0.59 ms | 0.20 ms | 0.92 ms |
| 256 个单位同时展开局部搜索 | 0.07 ms | 0.66 ms | 0.13 ms | 0.85 ms |

两个场景复用两万单位容量的实例。搜索场景只有 256 个活动单位，其余槽位停用；目标放在搜索窗口外，让 BFS 展开整个可达窗口。测试更换初始位置后先生成对应的初始视野，再测一个逻辑帧，避免把重新布置场景造成的集中揭图算作寻路耗时。准备阶段包括寻敌与局部寻路，结算阶段包括子弹、伤害、死亡、乘员和视野；不包含画面渲染或音频读回。原有两万活动单位开局场景的三个样本为 0.79、0.72、0.79 ms。

修复前的同帧死亡复现样本约为 16.65 ms，当时的战斗实例尚未包含视野更新。局部搜索的早期整帧样本约为 15.60 ms，但当时没有分段计时，不能把这个数单独归到 BFS。分段测量后移除了已规划相邻一步的重复流场计算，并区分了初始揭图的代价。上述性能检查已加入常驻浏览器检查。完整 Ultra 战斗的渲染帧率仍未实测。


## 击杀反馈与后续 review

按 EA 与 Nyerguds 的 `TECHNO.CPP`、`CREW.H` 和 `INFANTRY.CPP`，补上击杀记录、兴奋状态、庆祝动作和突击队员的四句嘲讽。普通步兵用击杀前的数量判断兴奋概率，因此第一次击杀不会触发；突击队员每次击杀都会触发。两秒的等待结束后，还要满足没有移动目的地、没有卧倒的条件。动作和语音分别按照 `InfantryClass::AI` 处理，庆祝动作使用 `MasterDoControls` 的两帧节拍。

击杀包含普通命中、连锁伤害和碾压。一帧内的死亡先按击杀者汇总，击杀者再按本帧的击杀序号取随机数，不使用线程或原子操作的先后顺序。`Kills` 保留原版无符号 16 位计数规则。浏览器对照场景增加了突击队员，检查 256 发同时命中只给一个死者记一次击杀，以及最后一次击杀两秒后的庆祝状态。

攻击目标失效后，按 `UnitClass::Enter_Idle_Mode` 与 `InfantryClass::Enter_Idle_Mode` 保留有效的移动目的地，先转为 MOVE，走到位后再警戒。使用局部路线时，会保留之前选好的最终开火位置。

BIKE 的 Risk 修正为 80。`UDATA.CPP` 中的 `80,45` 分别是 Risk 和 Reward；此前误读的 5 是出场关卡，错误来自提取数据时没有排除前面的条件编译分支。新增评分用例直接检查这个数值对近距离 HUNT 目标选择的影响。

胆怯步兵按 `InfantryClass::AI` 的实际调用 `Scatter(true)` 处理：参数是威胁坐标 1，即 `(1,0)`，并不代表强制散开。方向使用 `FACING8.ASM` 的规则，保留随机偏移和原版遍历全部八个邻格的顺序。在默认 `IsScatter=false` 且没有队伍管理的当前场景中，人类玩家单位不会执行这次自动逃跑。玩家主动下达的散开命令保持原有行为。

警戒的环形扫描补上与 HUNT 一致的 `targetable` 过滤，LST、炮艇和 Delphi 不会被自动选为地面目标。

HUNT 同分时仍按单位编号裁决。原版则保留地面图层排序中最靠前的对象，大致按纵坐标排列；这是当前实现与原版的差异。后续可以复用地面排序对齐。本轮按 review 建议保留 `solveRoutes` 的派发方式，间接派发留待后续优化。


本轮新增用例先复现了 8 处失败，覆盖击杀记录、攻击结束后继续移动、BIKE 的威胁评分、三种目标过滤，以及双方胆怯步兵的行为。补充检查还复现了庆祝动作被受伤卧倒提前打断，已按 `MasterDoControls` 的不可中断标志处理。

最终 `pnpm check` 输出 0 错误、0 警告；`pnpm test` 的 11 个文件、579 项测试通过，耗时 922 ms；`pnpm test:e2e` 的 8 项检查通过，输出 `browser checks passed (48.3s total)`。浏览器检查对照了新增击杀与庆祝状态、两种庆祝动作的原版 SHP 帧，以及 `LEFTY1`、`LAUGH1`、`KEEPEM1` 和 `TUFFGUY1` 的实际声音事件。

在同一 RTX 5090 D、驱动 32.0.16.1664、Chromium 156.0.8078.4 环境中，本轮两万活动单位开局 compute 样本为 0.85、0.85、0.92 ms；同帧死亡场景合计约 0.85 ms，256 个并行局部搜索场景合计约 0.92 ms，准备阶段约 0.07 ms。测量范围和前一节相同，不包含渲染与音频读回。

## AMD 核显验证

2026-10-24，使用 Ryzen 9 9950X 的 AMD Radeon(TM) Graphics 核显，驱动 32.0.21042.62，Chromium 156.0.8078.4。浏览器默认请求和 `low-power` 请求仍然返回 NVIDIA，因此本次测试通过 `--use-angle=d3d11 --use-adapter-luid=0,128170 --use-webgpu-power-preference=force-low-power` 指定核显。这个 LUID 来自本机 `chrome://gpu`，重启后可能变化。测试前确认活动设备为 AMD，实际 WebGPU adapter 返回 `amd`、`rdna-2`。

`pnpm check` 输出 0 错误、0 警告；`pnpm test` 的 11 个文件、579 项测试通过，耗时 894 ms；指定 AMD 运行的 `pnpm test:e2e` 共 8 项检查通过，输出 `browser checks passed (51.3s total)`。其中包含移动、战斗与视野的 CPU/GPU 状态对照，以及绘制、声音事件和设备丢失处理。

随后单独运行性能场景，避免其他浏览器检查同时使用 GPU。复用现有的 256×256 地图和两万单位容量；开局测第 3～5 个逻辑帧，另外两个场景各重新布置并测量 5 次。下表均为 GPU timestamp query 的 compute 耗时：

| 场景 | 样本范围 | 中位数 |
|---|---:|---:|
| 两万活动单位开局 | 7.14～9.50 ms | 7.41 ms |
| 两万个单位同帧死亡 | 12.85～13.70 ms | 12.91 ms |
| 256 个单位同时展开局部搜索 | 4.92～5.64 ms | 5.05 ms |

集中死亡场景的准备阶段为 6.03～6.16 ms，移动为 2.16～2.88 ms，结算与视野为 4.39～4.65 ms。因此不能把整个场景的耗时都归到死亡处理。局部搜索场景的准备阶段为 1.25～1.31 ms，其余单位槽位停用，与前述 NVIDIA 测量使用同样的场景定义。

这些数据不包含画面渲染和音频读回，也没有覆盖大量带有击杀归属的死亡或连锁爆炸。核显上的完整 Ultra 战斗帧率未实测。本次没有修改游戏代码，也没有 AMD 上的旧实现基线，因此这些结果只能说明当前版本在这张核显上的表现，不能据此判断近期修改有没有造成 AMD 性能回退。
